# DriveMate Parts V1 Deployment Notes

## Recommended Low-Cost Stack

```text
Vercel
├─ Next.js app hosting
├─ Preview deployments
└─ Environment variables

Supabase
├─ Postgres
├─ Auth
├─ Row Level Security
└─ Storage for account documents
```

This keeps early operations light: no VPS patching, no manual SSL, and no custom deployment scripts.

## Local Commands

```powershell
npm install
npm run preflight:local
```

`preflight:local` is the recommended local release gate before creating or promoting a Vercel preview. It runs
script syntax checks, TypeScript, unit tests, production build, Playwright browser tests, public-code sensitive
term scanning, local staging smoke checks, and resets local demo data after the smoke run.

For targeted checks during development, run individual commands:

```powershell
npm run typecheck
npm test
npm run build
npx playwright test
npm run dev -- --hostname 127.0.0.1 --port 3100
```

## Vercel Setup

1. Create a new Vercel project from the repository.
2. Set the project root to `apps/drivemate-web`.
3. Add environment variables from `.env.example`.
4. Use the default build command:

```text
npm run build
```

5. Use the default output generated by Next.js.

Recommended production values:

```text
NEXT_PUBLIC_SITE_URL=https://<production-domain>
DRIVEMATE_LEGAL_NAME=<registered company name>
DRIVEMATE_ABN=<company ABN>
DRIVEMATE_ACCOUNTS_EMAIL=accounts@<production-domain>
DRIVEMATE_WAREHOUSE_LABEL=Brisbane dispatch warehouse
DRIVEMATE_REPOSITORY=supabase
DRIVEMATE_ENABLE_DEMO_AUTH=false
NEXT_PUBLIC_SHOW_INTERNAL_NAV=false
SUPABASE_ACCOUNT_DOCUMENTS_BUCKET=account-documents
```

Keep `NEXT_PUBLIC_SHOW_INTERNAL_NAV=false` for the public website. Warehouse and admin users should enter through
authenticated internal links after Supabase Auth is connected.
The trade portal, warehouse, admin pages, and API responses are published with `X-Robots-Tag: noindex, nofollow`.
The HTML pages also include `noindex,nofollow` metadata, and `robots.txt` disallows `/portal`, `/warehouse`,
`/admin`, and `/api`. This keeps the public site discoverable while treating login, operations pages, and JSON
endpoints as controlled entry points rather than SEO landing pages.
The public `sitemap.xml` is generated from `NEXT_PUBLIC_SITE_URL` and intentionally includes only `/` and
`/catalogue`, so portal, warehouse, admin, and API routes are not submitted for indexing.

The app applies baseline security headers from `next.config.mjs` on every route:

```text
X-Content-Type-Options
X-Frame-Options
Referrer-Policy
Cross-Origin-Opener-Policy
Permissions-Policy
Strict-Transport-Security
```

`npm run verify:staging` checks these headers on public pages, along with hiding `x-powered-by`.
`npm run verify:release` also requires `NEXT_PUBLIC_SITE_URL` to be a real HTTPS public URL, and the staging smoke
check confirms `sitemap.xml` uses that value for the public home and catalogue URLs.
It also requires the business legal profile (`DRIVEMATE_LEGAL_NAME`, `DRIVEMATE_ABN`, and
`DRIVEMATE_ACCOUNTS_EMAIL`) so account documents do not launch with demo company details.

## Supabase Setup

1. Create a Supabase project in the region closest to the operating base.
2. Run SQL files in this order:

```text
supabase/schema.sql
supabase/policies.sql
supabase/seed.sql
```

If a staging Supabase project was already created from an earlier V1 schema, apply only the incremental migration
instead of re-running the full schema:

```text
supabase/migrations/20260530_add_vehicle_lookup_requests.sql
supabase/migrations/20260530_add_trade_order_pricing.sql
```

3. Confirm Row Level Security is enabled on exposed tables.
4. Create initial users and assign roles in `public.user_profiles`:

```text
trade       workshop portal users
warehouse   receiving / picking / dispatch users
admin       internal DriveMate operations users
```

## Frontend Login Flow

The portal, warehouse, and admin screens include a lightweight email/password login panel. When Supabase is
configured, client requests use:

```text
Authorization: Bearer <supabase_access_token>
```

When Supabase is not configured, local development falls back to the demo role header so the prototype remains
testable. Production should keep:

```text
DRIVEMATE_ENABLE_DEMO_AUTH=false
```

Required Supabase account setup:

```text
1. Create a user in Supabase Auth.
2. Insert a matching row into public.user_profiles using auth.users.id.
3. Set role to trade, warehouse, or admin.
4. For trade users, attach trade_account_id to the approved workshop account.
```

## Trade Account Applications

The public website includes an `Open Trade Account` form that posts to:

```text
/api/trade-account-applications
```

Applications are stored as pending `trade_accounts` rows and shown in the admin operational queue. The public
endpoint creates pending applications only. Admin users can approve pending applications through:

```text
/api/trade-account-applications/[applicationId]/approve
```

Approval changes the trade account status to `approved`. Admin users can also provision a workshop login through:

```text
/api/trade-account-applications/[applicationId]/provision-login
```

In Supabase mode this creates or reuses a Supabase Auth user, upserts the matching `user_profiles` row with
`role=trade`, links it to the approved `trade_account_id`, and returns a one-time temporary password only when a
new Auth user was created. Treat that temporary password as sensitive operational data and force rotation during
real onboarding.

Admin users can pause or reactivate an existing workshop account through:

```text
/api/trade-account-applications/[applicationId]/status
```

Only `approved` trade accounts can submit new orders. `pending`, `paused`, and `closed` accounts remain visible to
admin for review and exports, but they cannot create new stock reservations.

For staging, the setup can be created with the service-role bootstrap script:

```powershell
$env:DRIVEMATE_SEED_TRADE_EMAIL="trade@example.com"
$env:DRIVEMATE_SEED_TRADE_PASSWORD="<strong temporary password>"
$env:DRIVEMATE_SEED_WAREHOUSE_EMAIL="warehouse@example.com"
$env:DRIVEMATE_SEED_WAREHOUSE_PASSWORD="<strong temporary password>"
$env:DRIVEMATE_SEED_ADMIN_EMAIL="admin@example.com"
$env:DRIVEMATE_SEED_ADMIN_PASSWORD="<strong temporary password>"
npm run seed:users
```

The script creates or reuses:

```text
approved trade account
trade auth user + user_profiles row
warehouse auth user + user_profiles row
admin auth user + user_profiles row
```

Use staging-only emails and rotate passwords before any real production launch.

After the users exist, generate temporary access tokens for staging smoke checks:

```powershell
npm run smoke:tokens
```

The script signs in with the staging trade, warehouse, and admin emails/passwords and prints PowerShell
environment variable commands:

```text
DRIVEMATE_SMOKE_TRADE_TOKEN
DRIVEMATE_SMOKE_WAREHOUSE_TOKEN
DRIVEMATE_SMOKE_ADMIN_TOKEN
```

These are short-lived access tokens. Treat the output as sensitive, do not paste it into committed files, and
rerun the script when the tokens expire.

After Vercel has a preview or staging deployment, verify the deployed application itself:

```powershell
$env:DRIVEMATE_BASE_URL="https://<vercel-staging-url>"
npm run verify:staging
```

The staging verifier checks:

```text
health/readiness endpoint returns deployable configuration status
public website pages return 200
expected public-facing copy renders
internal commercial terms are not exposed in server-rendered pages
trade portal, warehouse, and admin pages are marked noindex/nofollow
internal pages and API responses include X-Robots-Tag noindex/nofollow
robots.txt disallows portal, warehouse, admin, and API paths
unauthenticated protected APIs return 403
optional trade / warehouse / admin token checks
optional public trade account application write check
optional trade lookup → trade order → warehouse dispatch → document access → admin order/document/lookup review e2e check
optional warehouse quarantine → QA release → QA write-off → admin audit check
optional admin SKU bulk import → fitment bulk import → warehouse bulk receiving → trade lookup → admin stock review check
optional account application → admin login provisioning check
deployed `/api/test/reset` returns 404
```

The public health endpoint is:

```text
/api/health
```

It intentionally returns only non-secret readiness data: repository mode, demo-auth visibility, public navigation
state, Supabase configuration presence, and document bucket name. In production it returns `503` when the app is
still configured for memory storage, demo role headers, visible internal nav, or missing Supabase variables.

For local prototype checks only, demo role headers can be enabled:

```powershell
npm run verify:staging
```

Local demo-header verification also checks purchase batch CSV export, warehouse quarantine QA release/write-off,
admin SKU import, fitment bulk import, warehouse barcode receiving, and trade lookup for the created SKU. For a real staging site, enable that write path only when the database can
accept a temporary test SKU and fitment rule:

```powershell
$env:DRIVEMATE_SMOKE_MASTERDATA_CHECK="true"
```

Local demo-header verification also checks account application and admin login provisioning. For a real staging
site, enable it only when Supabase Auth can accept a temporary test workshop user:

```powershell
$env:DRIVEMATE_SMOKE_ACCOUNT_PROVISION_CHECK="true"

```

```powershell

```

The e2e check performs real writes:

```text
trade token creates a test order
warehouse token dispatches that order
trade token reads invoice / delivery record / statement
trade token opens the invoice document link
admin token confirms the dispatched order appears in admin state
admin token confirms invoice and delivery document records appear in admin state
admin token confirms the trade lookup request appears in admin state
```

Run it only against staging stock that can be decremented or reset after testing.

and in Supabase-backed runtimes, and `verify:staging` checks that deployed URLs return `404`.

## Strict Release Readiness

Before using a Vercel deployment for real pilot operation, run the strict release gate from this directory:

```powershell
npm run verify:release
```

This command is intentionally stricter than `verify:staging`. It refuses localhost, requires an `https://` deployed
staging URL, requires Supabase mode, requires demo role headers and internal public navigation to be disabled, and
requires real trade / warehouse / admin smoke tokens.

Use an uncommitted local file for the release check values:

```text
.env.release.local
```

Minimum required release-check values:

```text
DRIVEMATE_BASE_URL=https://<vercel-staging-url>
DRIVEMATE_REPOSITORY=supabase
DRIVEMATE_ENABLE_DEMO_AUTH=false
NEXT_PUBLIC_SHOW_INTERNAL_NAV=false

NEXT_PUBLIC_SUPABASE_ANON_KEY=<supabase anon key>

DRIVEMATE_SMOKE_WAREHOUSE_TOKEN=<warehouse access token>
```

`verify:release` automatically runs:

```text

  with REQUIRE_SUPABASE_USERS=true
```

test account application, test SKU, test fitment rule, and test login provisioning are part of a planned operational
test and can be reviewed or removed afterwards.

## Current Demo Role Boundary

The current V1 skeleton can use the request header below to make role boundaries testable before real
Supabase Auth is connected:

```text
x-drivemate-role: trade | warehouse | admin
```

This demo role header is enabled only when:

```text
DRIVEMATE_ENABLE_DEMO_AUTH=true
```

If the variable is omitted, the header is enabled in local development and test, and disabled in production.
For a real launch, leave it disabled.

The portal, warehouse, and admin pages use a client-side role gate. In local development, missing Supabase client
configuration opens the workspace in demo mode so the prototype can be tested. In production, the same pages keep
the workspace locked until a signed-in Supabase user has the required `user_profiles.role`.

Current API restrictions:

```text
/api/vehicle-lookup        trade, warehouse, admin
/api/trade-state           trade, admin with explicit tradeAccountId
/api/orders                trade, admin
/api/inventory-movement    warehouse, admin
/api/inventory-movement/import warehouse, admin
/api/warehouse-state       warehouse, admin
/api/admin-state           admin
/api/admin-export          admin
/api/orders/[orderId]/cancel trade owner, admin
/api/health                public readiness metadata, no secrets
/api/products              admin
/api/products/import       admin
/api/products/[sku]        admin
/api/fitment-rules         admin
/api/fitment-rules/import  admin
/api/trade-account-applications public create
/api/trade-account-applications/[applicationId]/approve admin
/api/trade-account-applications/[applicationId]/provision-login admin
/api/trade-account-applications/[applicationId]/status admin
/api/test/reset            local memory-mode automation only, disabled when deployed
```

Production replacement:

```text
Supabase JWT
  ↓ joined with
public.user_profiles.role
  ↓ checked against
lib/auth.ts capabilities
```

For production API requests, browser clients should send the user's Supabase access token:

```text
Authorization: Bearer <supabase_access_token>
```

The server resolves the token through Supabase Auth, reads `public.user_profiles.role`, and then checks the
role against the capability required by each API route.

For trade users, order ownership is resolved server-side from `public.user_profiles.trade_account_id`.
The trade portal does not need to send `tradeAccountId`; production order creation does not trust any
client-provided account id. Staff/admin-created orders must provide the target trade account explicitly.
Order creation then checks `trade_accounts.status`; only `approved` accounts can submit or receive new orders.
Pending, paused, or closed accounts can still be reviewed by admin, but they cannot create fresh stock reservations.

## Data Persistence Note

The application now uses a repository interface:

```text
lib/repository.ts
├─ memory      default local prototype implementation
└─ supabase    Supabase-backed implementation skeleton
```

Use this environment variable to choose the runtime store:

```text
DRIVEMATE_REPOSITORY=memory
DRIVEMATE_REPOSITORY=supabase
```

`memory` is useful for prototype and tests. It resets when the server process restarts.

`supabase` expects:

```text
NEXT_PUBLIC_SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
```

The Supabase repository is designed to write/read:

```text
products
fitment_rules
inventory_balances
stock_movements
sales_orders
sales_order_lines
account_documents
vehicle_lookup_requests
pricing_rules
rfq_reviews
user_profiles
```

Warehouse users read operational data through `/api/warehouse-state`, which returns inventory rows, pick orders,
and recent stock movements without exposing the wider admin dashboard state. Trade order submission reserves
available stock; warehouse dispatch confirmation through `/api/orders/[orderId]/dispatch` releases the reserved
quantity and records a dispatch movement. The dispatch endpoint requires scanned SKU/barcode lines that match the
order lines, so warehouse users cannot complete an order dispatch without a pick confirmation scan.
Before dispatch, trade users can cancel their own submitted orders and admin users can cancel any submitted order.
Cancellation changes the order to `cancelled` and releases the reserved stock back to available inventory.

Warehouse users can also record putaway/bin transfer, returns, quarantine, and stock adjustment movements through
`/api/inventory-movement`. For first shipment receiving or spreadsheet-driven stock loads, warehouse users can
post up to 200 movement rows through `/api/inventory-movement/import`; each row is still processed through the
same inventory movement path, so every imported line creates a normal stock movement audit record.
Putaway moves stock from a receiving/source location to a shelf target location while keeping the same batch id.
It does not change total on-hand stock, but in Supabase mode it updates the source and destination
`inventory_balances` rows and records both `from_location_id` and `to_location_id`.
Quarantined stock remains physically on hand but is excluded from available stock, so it cannot be promised to
workshops until staff release or adjust it in a later workflow.
Quarantine review uses the same movement endpoint with `type=adjustment` and `quarantineAction=release` or
`quarantineAction=writeoff`. Release reduces quarantine and makes the unit available again; write-off reduces
quarantine and physical `on_hand`. Both paths require a QA/reference id and write an audit movement for the operator.
Stock adjustment is reserved for count corrections. It increases or decreases `on_hand` at the selected location,
does not change `reserved`, and records an `adjustment` movement with the count/reference id and operator.
Draft or paused SKUs can still be received, counted, adjusted, quarantined, or exported by staff, but they are
blocked from trade order submission. This lets the warehouse manage physical stock while admin controls when a SKU
is visible and orderable for workshops.

Warehouse scanner fields accept either the internal SKU, the product barcode, or mapped supplier/OEM aliases.
In Supabase mode, `/api/inventory-movement` resolves the scanned identifier against `products.sku`,
`products.barcode`, and `products.oem_part_number` before changing stock. This means the receiving and dispatch
screens can work with a normal keyboard-wedge barcode scanner as long as the product master data has been mapped.

Inbound receiving uses the `reference` field as the batch number and the `location` field as the warehouse bin.
Each inbound scan or bulk receiving row creates or updates an admin-visible purchase batch audit row with SKU,
batch number, received quantity, purchase reference, and received date.
Preferred bin format is:

```text
BNE-A01-03
```

Common operational aliases are also accepted:

```text
BNE receiving
BNE dispatch
BNE returns
BNE quarantine
```

In Supabase mode, inbound receiving, including bulk receiving imports, creates or reuses the matching
`inventory_locations`, `inventory_batches`, and `inventory_balances` rows, then writes a stock movement with
`batch_id` and `to_location_id`. Putaway then
moves that batch from the receiving/source balance to the shelf balance. Stock adjustment can correct a selected
location balance after a count check, while preserving an audit row. This keeps received stock traceable by SKU,
batch, and bin instead of treating the location field as a note.

Trade users read their own account state through `/api/trade-state`. The endpoint derives `tradeAccountId`
from `public.user_profiles.trade_account_id` for trade users, so the browser cannot select a different account.
It returns order history, server-calculated order totals, and released account documents from `account_documents`.

Trade prices are not accepted from the browser. The server derives order line prices from SKU pricing rules, stores
line ex-GST, GST, and inc-GST values on `sales_order_lines`, and stores order subtotal/GST/total on `sales_orders`.
Use `pricing_rules.unit_price_ex_gst_cents` as the V1 source of trade portal prices until a formal ERP/accounting
price list is connected.

Order submission creates a structured invoice record, and warehouse dispatch creates a structured delivery record.
The V1 uploads generated text account documents to Supabase Storage so the portal can open real document objects
through signed URLs. These documents include the configured legal profile, trade account, order reference, PO/job,
vehicle identifiers, and SKU quantities. Final priced invoices and statutory accounting PDFs should still be
generated by the accounting/PDF layer before production invoicing.
Order submission also ensures one monthly statement document per trade account and month, using a reference such
as `STMT-2026-05-<tradeAccountId>`.

Document opening is served through `/api/account-documents/[documentId]`. Trade users are scoped to their own
`trade_account_id`; admin users can use the endpoint for support checks. Supabase mode returns a short-lived
signed URL from the `SUPABASE_ACCOUNT_DOCUMENTS_BUCKET` bucket, defaulting to `account-documents`.

The admin backend also reads launch master data for SKU fitment rules, purchase batches, pricing rules, RFQ review
items, and user roles. These records are internal-only and should be validated in staging before live operations.
Trade vehicle lookups are recorded in `vehicle_lookup_requests` with the trade account, VIN/rego/query, matched
vehicle, match count, operator and timestamp. Use this as the first pilot demand log for missing fitment coverage,
supplier RFQ follow-up and SKU expansion decisions.
Admin users can export operating CSV snapshots from `/api/admin-export` for inventory, purchase batches, orders,
stock movements, account documents, lookup requests, reorder alerts, account applications, and trade accounts. Use those files for pilot reconciliation with warehouse counts,
workshop follow-up, replenishment planning, and manual accounting review until a formal accounting integration is
connected.
Admins can create product master records through `/api/products`, bulk import prepared SKU rows through
`/api/products/import`, then update scanner master fields through
`/api/products/[sku]`, currently covering `barcode`, `oemPartNumber`, `brand`, `name`, `category`, `status`,
`reorderPoint`, and `reorderQuantity`. The create endpoint captures the controlled SKU, brand, part name,
category, barcode, OEM part number, replenishment thresholds, and status. The import endpoint accepts up to 100
prepared rows and creates new SKUs or updates existing SKU master fields, which is the safer workflow for loading
the first pilot SKU list from the project spreadsheet. Fitment-rule maintenance is still a later
Admins can create fitment rules one by one through `/api/fitment-rules` or import prepared fitment rows through
`/api/fitment-rules/import`. The import endpoint accepts up to 200 rows with SKU, make, model, model-year range,
engine, and confidence. For the first pilot load, use the SKU import first, then fitment import, then run one
warehouse scanner check after any new SKU or master data change so the identifier and vehicle lookup are proven
before live receiving or dispatch work depends on them.
Admin state also returns a reorder alert list for active SKUs where available stock is at or below the SKU reorder
point. Use `reorderQuantity` as the default replenishment quantity for China-side RFQ or next shipment planning.

Before turning on `DRIVEMATE_REPOSITORY=supabase`, run `supabase/schema.sql`, `supabase/policies.sql`,
and `supabase/seed.sql` in the Supabase project and verify the seed includes starting inventory balances.

## Audit Trail

Server-side write operations pass the authenticated Supabase user id into repository writes:

```text
sales_orders.created_by
stock_movements.created_by
```

This is required for warehouse receiving, dispatch, trade order submission, and admin review. In local memory mode,
the same field is preserved for testability. In production, `created_by` should match the Supabase Auth user that
performed the action.

The admin backend displays this audit field in order and stock movement tables so staff can trace who submitted
an order, received stock, or dispatched stock. Local demo mode uses synthetic ids such as `demo-trade-user`.
