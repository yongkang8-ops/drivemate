## 1. 业务目标

让真实资料只提供箱组总数时，仍可确认 Packing List、准备产品标签、实点收货、暂存与上架。未知的逐箱分配明确保留为空，后续可以补录。补录装箱明细不会增加第二次收货或库存流水。

本轮只做本地开发与验证。GitHub 推送、数据库迁移、Vercel 部署及真实业务写入分别另行授权。

## 3. 已确认的代码现状与风险

- `lib/prearrivalShipment.ts` 的每个 carton 只有来源箱号、可选托盘号和 SKU 数量，没有实体箱数。
- `lib/warehouseDashboard.ts` 与 Pre-arrival 页面直接用 `cartons.length` 展示箱数，箱组会被误算为单箱。
- 标签、收货和上架通过 `shipmentId + cartonNumbers + SKU` 关联范围。仅更改页面文案不能解决数量投影。
- v20 确认函数会删除并重建当前 carton projection。后续补录若把一个已操作箱组改成多个独立收货范围，会改变其身份。
- 现有收货重复请求保护使用 idempotency key；这不等于已证明不同范围、不同 key 的所有重叠收货都安全。P1E 必须针对新引入的父子范围重叠验证，不能以原测试通过替代证明。

这些是本地代码检查结论，未向 Production 发起测试写入。

## 4. 方案选择

1. 等待取得逐箱数量：改动少，但当前文件无法提供，继续阻塞真实收货。
2. 保留稳定来源箱组，追加后补明细：推荐。能按已知总量工作，实际箱数正确，旧标签及收货保持可追溯。
3. 收货后将箱组替换为独立子箱：需要重新分摊已收货、已上架和标签范围，风险与本票需求不相称。

采用方案 2。后补明细为原箱组的追溯资料，不成为另一份待收货库存。

## 5. 版本化数据模型

新增明确的 `schemaVersion: 3`，避免旧 v2 代码静默丢弃箱组含义。继续接受 v1/v2；读取时按单箱规范化，不改写历史 snapshot，不从箱号字符串自动推断箱数。

v3 的 `cartons` 保留现有集合字段，但每条记录显式区分单箱与箱组：

```json
{
  "schemaVersion": 3,
  "shipmentId": "existing-shipment-id",
  "physicalPalletCount": 4,
  "cartons": [
    {
      "sourceCartonNumber": "7#8#9#",
      "kind": "carton_group",
      "physicalCartonCount": 3,
      "memberCartonNumbers": ["7#", "8#", "9#"],
      "sourcePalletNumber": null,
      "lines": [{ "sku": "DM-GWM-0064", "expectedQuantity": 10 }]
    }
  ]
}
```

### 校验

- `kind = carton`：实体箱数固定为 1，成员为自身来源箱号。
- `kind = carton_group`：实体箱数为大于 1 的整数；本期要求列出已知成员箱号，成员数量等于实体箱数。
- 来源范围标识在同一 shipment 内唯一。成员箱号不能重复、跨组，也不能同时成为独立单箱记录。
- SKU 数量是整个来源范围的合计，不乘以实体箱数。
- SKU、批次、正整数数量以及采购单范围校验延续已有要求。
- 箱组托盘字段只有在所有成员确实归属同一托盘时才能填写。未知或跨托盘时留空；不会阻碍业务。
- 后续来源修订必须保留已发生标签或收货操作的范围身份和数量事实。正常补充托盘映射仍可进行；结构或数量纠错应显式提示受影响记录，不允许悄悄重置已收货状态。

### 独立投影

- `sourceScopeCount = cartons.length`，本票 35。
- `physicalCartonCount = sum(carton.physicalCartonCount)`，本票 38。
- `cartonGroupCount = count(kind === carton_group)`，本票 2。
- `expectedQuantity = sum(all scope SKU quantities)`，本票 706。
- 未分配箱组数量单独展示，不能作为确认 Packing List 或实际收货的全局阻挡条件。

## 6. 标签、收货与上架

### 产品标签

- 支持全票、单箱、箱组和 SKU 范围。仍使用现有 `products.barcode`。
- 选择 7#8#9# 打印 10 张对应产品标签；选择 10#11# 同样打印 10 张。
- 组内各箱数量未知，不影响按组打印产品标签。
- 保留 Printed 手工确认及补打原因要求，不使用“发起打印”代替实体打印确认。
- 不向 7#、8#、9# 各打印一张写有“10 件”的外箱内容标签。未确认逐箱内容时，个别外箱不能标注组总量为其自身数量。
- 本轮不新增箱组条码制式，不改造承运商或发货标签。成员箱号可作为查询索引，但不能冒充独立、未收货范围。

### 收货

- 保留 `scan_each` 和 `counted_quantity` 两种方式。
- 分组收货以整个已选来源范围做实际清点，组总计 10 件时可逐件扫 10 次或识别条码后输入实点数量。
- 实点与预录入不一致时，继续使用已有差异原因和权限流程，不伪造每箱分配。
- 确认后进入 `BNE-RECEIVING-STAGING`，无需扫描来源货位。
- 本轮不额外引入“同一箱组反复确认部分收货”的新累计收货机制。现有收货草稿内可分批扫码；确认按选定范围核对总量。
- 成员箱号的查询只定位到所属组。收货提交包含未知范围、子箱范围或父子混合范围时，服务端明确拒绝，不能静默忽略。
- 后补装箱明细不产生新的可收货范围；组已收货后的重复确认及与全票范围重叠的提交必须纳入幂等/重叠回归检查。

### 上架与库存

- 沿用原收货会话，按产品数量扫描目标库位上架；允许按实际操作分批上架。
- 组内分配资料不更改可上架余额、已上架量或库存。
- Inventory 中库存件数不依赖箱数；箱数用于来源追溯，不能转为额外库存。

## 7. 后续补录的准确语义

新增组内装箱明细记录，始终关联原 shipment、来源箱组及作为依据的 Packing List revision。

- 明细记录采用只追加版本；更正须填写原因，保留前一版本、操作者、服务器时间和来源说明。
- 可先保存部分已知成员的 SKU 数量，未录入用空值，不把未知默认为 0。
- 明细只允许本组已列明的成员箱号。来源清单数量分配只允许本组 SKU；错误货品走收货异常记录。
- 页面明确区分 `Packing allocation`（装箱资料预期分配）与 `Observed contents`（到货实点观察），不能把实际短装修改成新的预期总量。
- 预期分配超过组内原 SKU 总量时不能保存为已核实分配；未足额时显示 Partial，全部成员已录且各 SKU 合计一致才显示 Complete。
- 实点观察允许短装、超收等真实差异并要求原因，状态显示 Difference。它不会确认收货、调整库存或替代正式差异处理。
- 保存后明确提示 `Carton details saved. Inventory has not changed.`。
- 没有逐箱资料时允许一直为空，不要求为了完成率填写推测数量。

## 8. 页面与权限

沿用已确认的 Operations Desk 设计、品牌色、字体、登录组件与英文文案，不更换全站设计系统。

- Pre-arrival 增加单箱/箱组类型、实体箱数和成员箱号字段；组内原 SKU 数量字段标明 `Group total`。
- 范围列表显示 `Cartons 7, 8, 9`，附 `3 physical cartons / 10 units` 与 `Per-carton quantities not recorded`。
- 顶部汇总分别显示实体箱数与来源范围数，不能混为一个 `Cartons` 指标。
- Warehouse 选择项显式带 `Group` 标识；固定展示当前选中范围和预期件数。
- 后补明细使用右侧抽屉，小屏全宽；有上方字段名、字段下错误、保存中、失败保留输入、成功反馈和未保存离开确认。
- Dashboard 只读展示物理箱数、组数及资料完整度；资料未补齐显示信息提示，不把正常收货误标为失败。
- History 增加装箱明细版本事件，显示日期、时间、时区、操作者、原因、结果；库存汇总不把该事件计入收货数量。
- 创建/确认来源清单及提交组内明细沿用 `prearrival_manage`（admin/partner）；不新增公开入口、不调整 Staff 角色。
- warehouse_staff 继续正常打印、收货、上架和查看相关历史；实际收货数量仍在既有操作台录入。
- 成本与单价仍只展示给现有授权角色。产品标记、认证资料、适配证据不因本轮来源核对获得自动发布资格。

## 9. 持久化和接口范围

拟新增 v21 本地迁移，保留 v20 作为已完成依赖，不改写既有迁移历史。

- 当前 `shipment_cartons` 投影保存记录类型、实体箱数和成员箱号；shipment 内成员互斥由确认事务同时校验。
- 确认函数增加 v3 分支；旧 v1/v2 保持可读，不将历史裸字符串自动解析成箱组。
- 新增只追加的装箱明细版本表，记录 shipment、source scope、Packing List revision、明细类型、payload、原因、操作者、时间、幂等键及前一版本。
- 新增私有 shipment carton-details GET/POST 接口；写入采用原子事务校验当前范围、版本和权限，拒绝失效基线的覆盖请求。
- 补录接口不调用收货/上架接口，不更新 stock balances、stock movements 或 receipt session。
- Memory repository 与 Supabase repository 采用相同领域校验；API、数据库与前端三层均拒绝非法父子范围或数量输入。
- 审计表和补录记录同事务提交；回滚失败不允许留下“成功”历史。

实现涉及 `lib/prearrivalShipment.ts`、`lib/prearrivalDraftValidation.ts`、`lib/warehouseLabels.ts`、`lib/warehouseInboundScope.ts`、`lib/warehouseDashboard.ts`、`lib/warehouseHistory.ts`、两个 repository、对应 API 与现有操作台组件。后补校验放在独立小模块，不继续堆入页面组件。

## 10. 本地验证与发布检查

1. v1/v2 兼容；v3 单箱、箱组混用，全部无托盘/部分托盘映射通过。
2. 本票精确投影：35 来源范围、38 实体箱、2 多箱组、119 SKU、706 件、4 托且未映射。
3. 两组打印分别 10 张；全票产品标签数量 706，不因实体箱数倍增。
4. 两种收货模式各完成本地组范围收货；暂存、上架、库存、历史数量一致。
5. 补录前后旧 print payload、收货会话、库存余额及 stock movement 数量完全不变。
6. 重复成员、范围重叠、空成员、非整数箱数、箱数不匹配、SKU 越界、超额预期分配、失效版本提交均有明确错误。
7. 实点观察差异不会自动改写期望值；保存、修订、并发重试均有可追溯结果。
8. 用不同幂等键尝试对同一已收范围重复确认，以及全票和箱组重叠确认；确保不会因 P1E 新表示重复入库。发现原有缺陷需报告和明确最小修复范围，不宣称已安全。
9. 仅分箱资料不全时不阻挡业务；缺真实产品条码、无权限、失效会话等错误仍准确提示。
10. Vitest、typecheck、生产构建、聚焦浏览器用例；390/701/768/880/1280px 布局和键盘操作检查。
11. 新迁移须在隔离本地 PostgreSQL/Supabase 执行验证关键事务；静态 SQL 文本测试不能替代数据库运行验证。环境缺失则明确报告未验证，不连接 Production 替代。
12. QA 报告分别记录通过、失败、未验证项目，并提供本地浏览器入口或截图。
